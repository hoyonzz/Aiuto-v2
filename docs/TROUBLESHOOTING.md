## 1. 포괄적 예외 처리가 서로 다른 버그 두 개를 숨긴 사례

### 문제 상황

로그인 인증 부분(`get_current_user`)을 동기에서 비동기로 전환하던 중,
코드를 수정하고 애플리케이션을 실행해 요청을 보내면 계속 401 에러가
반환됐다. 새로 발급받은 토큰으로 다시 시도해도 결과는 같았다.

```python
try:
    payload = jwt.decode(token)
    ...
except Exception:
    raise credentials_exception
```

### 원인

`except Exception:`이 모든 에러를 잡고 있어 실제 원인이 드러나지 않았다.
로직을 단위별로 나눠 디버깅한 결과, 원인은 두 개였다.

첫 번째는 잘못된 설정값 이름이었다.

```
>>> setting.SECRET_KEY
AttributeError: 'Settings' object has no attribute 'SECRET_KEY'
```

두 번째는 `jwt.decode()`의 필수 인자 누락이었다.

```
>>> jwt.decode(token)
DecodeError: It is required that you pass in a value for the "algorithms"
argument when calling decode().
```

두 에러 모두 `except Exception:`에 걸려 401 인증 실패로 일괄 처리되면서
실제 원인이 가려졌다. 인증 로직은 한 번도 정상적으로 실행된 적이 없었는데,
겉으로는 토큰 문제로만 보였다.

### 해결

`except Exception:`을 발생 가능한 에러 타입으로 좁혔다.

```python
except (jwt.PyJWTError, ValueError):
    raise credentials_exception
```

범위를 좁히자 두 에러가 그대로 노출됐다. 설정값 이름을 수정하고
`jwt.decode()`에 필수 인자(`key`, `algorithms`)를 명시했다. 이후 정상 토큰,
위조된 토큰, 만료된 토큰, 형식이 잘못된 값을 각각 입력해 의도한 인증
예외만 처리되는지 검증했다.

### 느낀 점

`except Exception`을 습관적으로 사용해왔는데, 이번에 그 방식이 오히려 버그를
가린다는 것을 확인했다.

이후로는 예외 처리를 작성할 때 해당 지점에서 발생 가능한 에러부터 따져보고,
그 타입만 명시적으로 처리하게 됐다.

## 2. 파싱이 실패했는데 예외가 나지 않은 사례

### 문제 상황

Gemini API에 `response_schema`를 전달해 구조화 출력을 요청하는 클라이언트를
구현하면서, 파싱 실패 시 `pydantic.ValidationError`가 발생할 것으로 보고 예외
처리 블록을 함께 작성했다. 그런데 그 블록이 한 번도 실행되지 않아
확인해보니, 에러 없이 `response.parsed`가 `None`으로 반환되면서 파싱 실패가
정상 응답처럼 넘어가고 있었다.

### 원인

`google-genai` SDK 소스를 직접 열어본 결과, 응답을 파싱하는 `_from_response`
안에서 `pydantic.ValidationError`와 `json.JSONDecodeError`를
`try/except: pass`로 무시하고 있었다. 파싱이 실패해도 예외를 밖으로 던지지
않고 `parsed` 속성만 비워두는 구조였고, 공식 문서에는 이 동작이 드러나지 않아
내가 작성한 `except` 블록은 데드 코드로 남아 동작하지 않았다.

### 해결

예외 발생을 기다리는 방식으로는 실패를 감지할 수 없으므로,
`response.parsed is None`을 명시적으로 검사하도록 변경했다. 다만 `None`이라는
사실만으로는 재시도 여부를 판단할 수 없어, `candidates[0].finish_reason`을
직접 읽어 실패 사유를 구분하는 로직을 추가했다.

사유 판별은 처음에 `SAFETY`, `PROHIBITED_CONTENT` 같은 차단 사유를 나열하는
방식으로 작성했다가 `PROHIBITED_CONTENT`를 빠뜨렸다. 차단 사유는 앞으로도
추가될 수 있어 나열하는 한 누락 위험이 남기 때문에, 조건을 반전시켜 정상
종료(Gemini 기준 `STOP`, `MAX_TOKENS`)일 때만 재시도 대상으로 분류하고
나머지는 전부 영구 실패로 처리하도록 바꿨다.

검증은 `generate_content`를 Mock으로 대체해 응답을 원하는 상태로 만들어
진행했다. 정상 응답, 세이프티 차단, 파싱 실패, 토큰 초과, 빈 응답 시나리오를
구성해 각 분기가 의도대로 동작하는지 확인했다.

### 느낀 점

애플리케이션 코드뿐 아니라 외부 라이브러리도 예외를 삼킬 수 있다는 것을
확인했다.

이후로는 라이브러리를 쓸 때 "발생할 수 있는 예외"를 먼저 파악하게 됐다.
문서에 드러나지 않는 부분은 소스를 열어보거나 Mock으로 직접 검증해야 한다는
것을 배웠다.

## 3. 추론 과정이 출력 필드에 혼입된 사례

### 문제 상황

"내일 오전 10시에 알고리즘 복습" 같은 일정을 입력하면 `title` 필드에 모델의
계산 과정이 그대로 들어갔다. 한국어 사이에 영어 자기 교정 문장까지 섞였고,
정작 필요한 `start_at`은 `None`으로 반환됐다.

재현도 일정하지 않았다. 전날 같은 문장으로 실행했을 때는 정상 출력이
나왔기 때문에 원인을 특정하기가 더 어려웠다. 게다가 검증 코드가 `intent`만
확인하고 있어 테스트는 계속 통과했다.

### 원인

처음에는 Thinking Budget을 최소로 설정한 것을 원인으로 봤다. 의도별로 나눠
확인해보니 `task`, `memo`, `research`는 정상 동작했고 `schedule`에서만 문제가
발생했다. 원인을 유추해보니 네 의도 중 시각 계산이 필요한 것은 `schedule`뿐
이었다.

당시 프롬프트는 모델에게 현재 UTC 시각을 주고 KST와의 9시간 차이를 직접
계산하도록 지시하고 있었다. 계산은 수행해야 하는데 그 결과를 담을 자리가
없다 보니 추론 과정이 출력 필드로 유출된 것으로 판단했다. Thinking Budget을
늘리면 발생 확률은 낮아지겠지만, 모델에게 연산을 맡기는 구조가 유지되는 한
언제든 재발할 수 있었다.

### 해결

설정을 조정하는 대신 모델과 코드의 역할 분담을 바꿨다.

1. 파이썬이 "오늘/내일/모레"에 해당하는 날짜를 미리 계산해 프롬프트에 표로
   주입하도록 했다. 모델은 날짜를 계산하지 않고 표에서 찾기만 하면 됐다.
2. 모델은 시간대 변환 없이 로컬 시각만 출력하도록 했다. 9시간을 빼는 연산
   자체가 사라졌다.
3. UTC 변환은 `ZoneInfo`를 사용해 파이썬이 처리하도록 옮겼다.
4. 프롬프트에 "각 필드에는 최종 값만 넣고 설명이나 계산 과정을 포함하지
   마라", "title은 30자 이내" 규칙을 추가했다.

검증 코드도 함께 수정했다. `intent`만 확인해서는 이번 문제를 잡을 수 없으므로,
`start_at`이 실제로 의도한 시각인지, `title` 길이가 정상인지, 비정상 추론
텍스트가 포함되지 않았는지까지 확인하도록 바꿨다.

### 느낀 점

모델이 잘하는 일과 신뢰하기 어려운 일이 다르다는 것을 확인했다. 자연어에서
의미를 추출하는 작업은 안정적이지만 정확한 산술은 맡기기 어렵다. 결정론적으로
계산할 수 있는 부분은 코드가 처리하는 편이 맞다.

검증 설계 측면의 교훈이 더 컸다. 필드가 존재하는 것과 값이 올바른 것은 다른
문제인데 `intent`만 확인하고 통과로 처리하고 있었다. 검증 항목을 정할 때 존재
여부뿐 아니라 값의 정확성까지 확인해야 한다는 것을 깨달았다.

## 4. 프롬프트를 수정할 때마다 다른 케이스에서 회귀가 발생한 사례 (3회 연쇄)

### 문제 상황

"오늘 자정에 마감"의 `start_at`이 오늘 00:00, 즉 이미 지나간 시각으로
계산됐다. "오늘 자정"은 통상 오늘이 끝나는 시점인 내일 00:00을 뜻하는데,
모델이 기준 날짜 매핑 표(앵커)의 날짜에 00:00을 문자 그대로 결합한 것이다.

이 문제를 수정하는 과정에서 같은 유형의 회귀를 세 번 겪었다.

### 원인

**1차.** 자정 문제를 수정하면서 규칙 두 개를 추가했다. "자정은 내일 날짜의
00:00으로 계산하라"와, 안전장치로 넣은 "계산된 시각이 현재보다 과거면 안
된다"였다.

자정은 해결됐지만 "3시간 뒤에 전화하기"에서 문제가 발생했다. 원래는 모델이
현재 시각을 모르기 때문에 계산을 포기하고 `task` + `start_at=None`으로
안전하게 실패하던 입력이다. 그런데 `schedule`로 분류하고 13시간 넘게 지난
시각을 생성하기 시작했다. 현재 시각을 모르는 상태에서 "과거 금지"만
지키려다, 모순된 제약을 만족시키려는 방향으로 존재하지 않는 시각을 만들어낸
것으로 판단했다. 안전장치로 넣은 규칙이 오히려 허위 값을 유도한 셈이다.

규칙을 제거하고 다시 확인해보니 자정 문제는 첫 번째 규칙만으로 이미
해결된 상태였다. 필요하다고 판단해 추가한 규칙이었지만, 다른 케이스의
결과까지 바꿀 수 있다는 것을 예상하지 못한 것이 원인이었다.

**2차.** 할 일에서 마감 날짜를 추출하는 규칙("마감이 언급되면 `due_date`를
채워라")을 추가했다. 그러자 "오늘 자정에 프로젝트 마감이야"가 `task`로
분류됐다. 자정이라는 고정 시각이 있으므로 `schedule`이어야 하는데,
"마감"이라는 단어가 분류에 더 강하게 작용한 것으로 판단했다. "마감과 함께
고정 시각이 언급되면 `schedule`"이라는 우선순위 규칙을 추가해 해결했다.

**3차.** 2차 수정에 넣은 예시 문구가 문제였다. 예시로 "3시"를 사용했는데,
그 때문에 "3시간 뒤에 전화하기"가 다시 `schedule`로 분류되고 과거 시각을
생성했다. "3시"(고정 시각)와 "3시간"(기간)이 문자열로 겹쳐 표면적인 패턴
매칭을 유발한 것으로 판단했다. 예시를 "오후 5시"로 교체하고 "N시간·N분 뒤는
고정 시각이 아니다"를 명시해 해결했다.

### 해결

개별 수정만으로는 회귀를 막을 수 없다고 보고, 프롬프트를 한 줄이라도 고치면
스모크 세트 전체를 처음부터 다시 실행하는 절차를 세웠다. 2차와 3차 회귀는
그렇게 해서 발견한 것으로, 수정한 케이스만 확인했다면 전부 놓쳤다.

### 느낀 점

프롬프트 수정은 계획한 부분 이외에도 영향을 미칠 수 있으니, 수정할 때는
전체적으로 어떻게 달라졌는지 직접 테스트해보고 확인해야 한다는 것을 깨달았다.

## 5. 폴백 테스트 방법을 검토하다 폴백 자체의 결함을 발견한 사례

### 문제 상황

LLM 프로바이더 호출이 실패하면 다음 프로바이더로 넘기는 폴백 체인을
구현했다. Mock 클라이언트로 시나리오를 구성해 검증까지 마친 상태에서,
실제 네트워크 장애를 어떻게 재현해 확인할지 검토하다가 문제를 발견했다.

### 원인

`gemini.py`는 `except APIError`만 잡고 있었다. SDK 소스를 확인해보니
`google-genai`는 HTTP 에러 응답(401, 429, 500 등)만 `APIError`로 감싸고 연결
자체가 실패하는 상황은 감싸지 않아, `httpx.ConnectError`나
`httpx.TimeoutException`이 원본 그대로 전파되면서 폴백 체인이 잡지 못하고
전체가 중단되는 것을 재현해 확인했다.

이 예외는 내가 정의한 일시적 오류에도 영구적 오류에도 해당하지 않았다. 설계
문서에는 "네트워크 장애는 폴백 대상"이라고 명시해뒀는데, 정작 가장 흔한
네트워크 장애가 처리되지 않는 상태였다.

같은 코드를 옮겨 구현한 다른 클라이언트에는 이 문제가 없었다. `openai` SDK는
연결 장애를 자체적으로 감싸서 던지기 때문이다. SDK마다 예외를 감싸는 범위가
다른 것이 원인이었다.

### 해결

연결 실패와 타임아웃을 일시적 오류로 분류하는 처리를 `APIError`보다 먼저
추가했다. `httpx.TransportError` 하나로 전부 잡을 수도 있었지만, 거기에는
설정 오류처럼 내 쪽에서 발생하는 예외도 포함되어 폴백이 순회하다 전부
실패하면서 실제 원인이 드러나지 않는다. 그래서 타임아웃, 네트워크 오류,
프록시 오류만 선별해서 처리했다.

이후 한 번 더 문제가 있었다. 이 수정을 반영하고 확인까지 마쳤는데, 다른
기능을 작업하면서 같은 파일을 다시 편집하는 과정에서 해당 블록이 통째로
빠졌다. 그 상태로 완성본이 됐고, 커밋 직전 전체 재실행에서 발견했다.

### 느낀 점

테스트 방법을 검토하는 것만으로 설계 결함이 드러났다. 어떻게 검증할지에 대한
답이 잘 나오지 않는다면 검증이 어려운 것이 아니라 설계가 덜 된 것일 수 있다는
것을 확인했다.

## 6. 에러 없이 통과했지만 DB 제약이 누락된 사례

### 문제 상황

비동기 파이프라인용 도메인 테이블 네 개를 정의하고 마이그레이션을 적용했다.
모델 정의, 마이그레이션 생성, 적용까지 에러 없이 전부 통과했고 코드를
읽어도 `sa.Enum`을 정상적으로 사용한 것처럼 보였다.

문제는 단계를 마친 뒤 DB가 의도대로 구축됐는지 하나씩 대조하는 과정에서
드러났다. 예외가 아니라 검증 절차가 찾아낸 문제였다.

### 원인

`sa.Enum`에 제약 조건을 거는 방식을 구현할 때 참고한 자료가 SQLAlchemy 1.x
기준이었고, 버전이 맞는지 확인하는 절차가 없었다. 2.0에서는 `sa.Enum`의
`create_constraint` 기본값이 `True`에서 `False`로 변경됐는데, 그 사실을 모른
채 구현한 것이다.

`\d`로 실제 DB 스키마를 조회하니 `Check constraints` 섹션이 비어 있었고,
`pg_constraint`를 직접 조회해도 0건이었다. `native_enum=False`로 사용하면
DB에는 `varchar`로 생성되는데, `create_constraint`를 명시하지 않아 값을
강제하는 CHECK 제약이 붙지 않은 것이다.

애플리케이션 레벨에서는 Python `Enum`이 잘못된 값을 차단하고 있어 겉으로는
문제가 없어 보였지만, 데이터 무결성이 ORM 계층에만 의존하는 상태였다.

### 해결

`create_constraint=True`를 명시하고, 수정 마이그레이션을 덧대기보다 초기
마이그레이션을 처음부터 다시 생성했다.

검증은 ORM이 아니라 raw SQL로 직접 INSERT를 시도하는 방식으로 진행했다.
ORM을 거치면 Python `Enum`이 먼저 차단해 DB 제약이 있든 없든 동일하게
실패하기 때문에, 정의에 없는 문자열을 raw SQL로 입력했을 때 DB가
`IntegrityError`를 반환하는 것까지 확인하고 통과로 판정했다.

### 느낀 점

프로젝트에 사용하는 프레임워크나 라이브러리는 메이저 버전을 정확히 확인하고,
변경된 동작이나 기본값을 함께 확인해야 한다는 것을 배웠다.

이번 문제는 코드에서는 드러나지 않고 DB를 직접 확인하는 과정에서 발견됐다.
구현이 끝난 뒤 실제 결과물을 직접 확인하는 절차가 필요하다는 것을 깨달았다.

## 7. 시각 변환 책임이 두 계층에 나뉘어 있던 사례

### 문제 상황

3번에서 시각 계산을 모델에게서 코드로 옮긴 뒤로는 정상 동작하는 것처럼
보였다. 그런데 비동기 파이프라인을 붙이고 나서 오후 3시로 입력한 일정이
전날 21시로 저장되기 시작했다. 한국 시간과 UTC의 차이인 9시간이 정확히
두 번 빠진 값이었다.

### 원인

시각을 UTC로 바꾸는 작업을 두 곳에서 하고 있었다. 화요일 오후 3시(KST)
입력에 대해 정상이라면 `2026-09-15 06:00+00`으로 저장돼야 하는데
`2026-09-14 21:00+00`이 저장됐다. LLM 클라이언트가 한국 시간을 UTC로 변환해
넘겼는데, 워커는 그 값을 아직 변환되지 않은 한국 시간으로 보고 9시간을 한 번
더 뺀 것이다.

원인은 계산 오류가 아니라 누가 변환을 책임지는지 정해두지 않은 것이었다.
클라이언트는 자신이 변환했으니 끝났다고 보고, 워커는 아직 변환되지 않았다고
가정했다. 한쪽 코드만 보면 양쪽 다 맞아 보이기 때문에, 두 곳을 함께 놓고
봐야 드러나는 문제였다.

시각이 틀려도 에러는 발생하지 않는다. 9시간 어긋난 값도 형식상으로는 정상적인
시각이기 때문에, 저장된 값을 직접 확인하기 전까지는 알 수 없었다.

### 해결

처음에는 워커가 받은 값에 시간대 정보가 붙어 있는지 확인해서, 이미 변환된
값이면 건너뛰도록 수정했다. 증상은 사라졌지만 변환 책임은 여전히 두 곳에
남아 있었다. 나중에 변환하지 않고 값을 넘기는 프로바이더가 추가되면 같은
문제가 다시 발생할 수 있는 구조였다.

그래서 책임을 한쪽으로 정하는 방향으로 다시 수정했다.

> LLM 클라이언트는 항상 UTC로 변환한 시각을 반환한다.
> 워커는 시간대 변환을 하지 않는다.

이 규칙을 레포의 규칙 문서에 명시하고 워커 쪽 확인 코드를 제거했다. 어느
계층이 무엇을 책임지는지는 코드만으로 강제할 수 없기 때문에, 프로바이더가
늘어나도 지켜야 할 기준이 문서에 남아 있도록 했다.

### 느낀 점

시간대 변환을 대수롭지 않게 생각하고 있었는데, 이번 문제를 겪으면서 일정을
다루는 서비스에서 시각이 얼마나 중요한 값인지 알게 됐다. 특히 같은 처리를
여러 곳에서 할 수 있는 경우에는 누가 그 일을 책임지는지 정해두는 것이
중요하다는 것을 확인했다.

이 규칙을 문제가 발생한 뒤에 정했는데, 계층을 나누는 설계 단계에서 미리
정해뒀어야 하는 부분이었다. 그리고 이 문제 자체가 저장된 값을 직접 확인하는
과정에서 드러났기 때문에, 결과를 눈으로 검증하는 절차가 계속 필요하다는 것도
함께 깨달았다.

## 8. 커밋되지 않은 상태 변경이 중복 실행 방어를 통과시킨 사례

### 문제 상황

README와 코드를 대조하던 중 중복 실행 방어에 구멍이 있는 것을 발견했다.
워커의 태스크는 `job.status`가 `SUCCESS`일 때만 처리를 건너뛰고 있었다.

`celery_app.py`에 `task_acks_late=True`를 설정해 워커가 중단되면 태스크가
재배달되도록 해뒀는데, 정작 가드는 이미 끝난 작업의 재실행만 막고 있었다.
처리 도중에 중단되어 `PROCESSING`으로 남은 작업이 재배달되면 그대로
통과하는 상태였다.

### 원인

가드를 `if job.status != AiJobStatus.PENDING: return`으로 바꿨다. 코드만
읽으면 `PROCESSING`도 걸러지므로 해결된 것처럼 보였다.

그런데 `get_sync_db()`가 `with` 블록 전체를 하나의 트랜잭션으로 묶기 때문에,
`PROCESSING`으로 바꾼 변경이 LLM 호출이 끝날 때까지 커밋되지 않는다.
PostgreSQL의 기본 격리 수준인 Read Committed에서는 커밋된 데이터만 읽을 수
있으므로, 그 사이에 다른 프로세스가 같은 작업을 읽으면 여전히 `PENDING`으로
보인다. 가드가 있어도 통과한다.

수정이 실제로 통하는지 재현 스크립트로 확인했다. `PENDING` 상태의 작업
하나를 만들고 같은 태스크를 0.4초 간격으로 두 번 큐에 넣었더니, 두 태스크가
모두 성공으로 끝나고 각각 다른 `ref_id`를 반환했다. DB에는 동일한 사용자·
동일한 내용으로 `memos` 두 행이 생성돼 있었고, `ai_jobs.result_ref_id`는
나중에 커밋한 쪽만 가리켜 먼저 생성된 memo는 참조가 끊긴 채 남았다.

### 해결

가드 조건을 바꾸는 것으로는 해결되지 않는다고 보고 트랜잭션 구조를 다시
설계했다.

작업을 집는 동작을 `UPDATE ai_jobs SET status = 'PROCESSING' WHERE id = ?
AND status = 'PENDING' RETURNING raw_text`로 바꿨다. 조건 검사와 상태 변경이
한 문장 안에서 일어나므로 두 프로세스가 동시에 실행해도 한쪽만 성공한다.
이 UPDATE는 별도의 짧은 트랜잭션으로 즉시 커밋한다.

LLM 호출은 이 트랜잭션 밖으로 뺐다. 응답까지 수 초가 걸리는 작업을 트랜잭션
안에 두면 그동안 다른 프로세스가 커밋 전 상태를 보게 된다. 결과적으로 태스크
하나가 선점 · LLM 호출 · 결과 기록 세 개의 구간으로 나뉘고, 트랜잭션은 첫
번째와 세 번째에만 존재한다.

같은 시나리오로 다시 확인했다. 첫 번째 태스크는 정상 처리됐고(2.14초),
두 번째는 선점에 실패해 아무 작업도 하지 않고 0.03초 만에 반환됐다. LLM
호출 자체가 발생하지 않았다. DB에는 memo가 하나만 생성됐고
`result_ref_id`가 그 memo를 정확히 가리켰다.

### 느낀 점

설계할 때부터 중복 실행이 생길 수 있다고 보고 가드를 넣어뒀는데, 그 가드가
의도대로 동작하지 않는다는 것을 테스트에서야 확인했다. 설계에서 예상한
것과 실제로 동작하는 것이 다를 수 있다는 것을 직접 겪었다.

처음에는 조건 하나만 고치면 끝날 문제로 보고 넘어가려 했다. 실제로 통하는지
확인해보지 않았다면 그대로 남았을 문제였고, 지금 해결하고 넘어간 것이 맞다고
생각한다.

원인을 추적하면서 트랜잭션 격리 수준이라는 개념을 새로 알게 됐다. 조건문
하나로 막을 수 있다고 생각한 문제가 실제로는 트랜잭션을 얼마나 길게
잡았느냐의 문제였고, LLM 호출처럼 수 초가 걸리는 외부 요청을 트랜잭션 안에
두면 그동안 다른 프로세스가 옛 상태를 보게 된다는 것을 이번에 배웠다.

## 돌아보며

여덟 개를 정리하고 나서 보니 대부분이 같은 문제였다. 실패했는데 실패한 것처럼
보이지 않았다는 것이다. 내가 쓴 `except`가 에러를 가렸고(1), 라이브러리가
예외를 삼켰고(2), 검증 코드가 필드 존재만 확인해 테스트가 계속 통과했고(3),
DB에는 제약이 붙지 않았는데 애플리케이션에서 막아주고 있어 문제가 드러나지
않았다(6). 시각이 9시간 틀린 값도 형식상으로는 정상이라 에러가 나지 않았다(7).

예상한 에러와 결과가 실제로 그렇게 나오는지 직접 확인해야 한다는 것을
깨달았다. 지금은 구현이 끝나면 저장된 값과 실제 DB 상태를 직접 조회해
의도한 대로 동작하는지 검증하고 있고, 실제로 이 과정에서 여러 문제를 찾았다.

8번은 여기서 한 걸음 더 나갔다. 문제를 고친 뒤에도 그 수정이 실제로 통하는지
확인해야 한다는 것을, 확인하지 않았으면 그대로 넘어갔을 사례로 배웠다.
