## 1. 포괄적 예외 처리가 서로 다른 버그 두 개를 숨긴 사례

### 문제 상황

로그인 인증 부분(`get_current_user`)을 동기 코드에서 비동기 코드로 바꾸던
중이었다. 코드를 고치고 서버를 켜서 확인하면 항상 401 에러만 떴다. 새로
로그인해서 토큰을 다시 받아 시도해도 마찬가지였다.

```python
try:
    payload = jwt.decode(token)
    ...
except Exception:
    raise credentials_exception
```

### 원인

`except Exception:`으로 모든 에러를 다 잡고 있어서, 진짜 원인이 뭔지 전혀 안
보이는 상태였다. 하나씩 직접 실행해보면서 확인했더니 실제로는 두 가지가
잘못돼 있었다.

첫 번째는 설정값 이름이 잘못돼 있었다.

```
>>> setting.SECRET_KEY
AttributeError: 'Settings' object has no attribute 'SECRET_KEY'
```

두 번째는 `jwt.decode()`에 필요한 값을 안 넣고 부르고 있었다.

```
>>> jwt.decode(token)
DecodeError: It is required that you pass in a value for the "algorithms"
argument when calling decode().
```

두 에러 다 `except Exception:`에 걸려서 그냥 "토큰이 잘못됐다"는 401로
뭉뚱그려지고 있었다. 로직 자체가 한 번도 제대로 실행된 적이 없었는데,
겉으로는 그냥 인증 실패처럼 보였던 거다.

### 해결

`except Exception:`을 실제로 예상 가능한 에러 타입으로 좁혔다.

```python
except (jwt.PyJWTError, ValueError):
    raise credentials_exception
```

이렇게 하니 위 두 에러가 숨지 않고 그대로 드러나서 바로 원인을 알 수 있었다.
그다음 설정값 이름을 고치고, `jwt.decode()`에 키·알고리즘을 채워 넣었다.
그리고 정상 토큰, 위조된 토큰, 만료된 토큰, 형식이 잘못된 값을 각각 직접
넣어보면서 의도한 대로만 걸러지는지 하나씩 확인했다.

### 느낀 점

에러 처리할 때 `except Exception`을 습관처럼 썼었는데, 이번에 그게 오히려
버그를 못 보이게 만든다는 걸 직접 겪었다. 지금은 예외 처리를 쓸 때 "여기서
실제로 나올 수 있는 에러가 뭐지"를 먼저 생각하고 그것만 잡으려고 한다.

## 2. SDK가 예외를 내부에서 삼켜 파싱 실패가 조용한 None이 된 사례

### 문제 상황

Gemini에 `response_schema`로 구조화 출력을 요청하는 클라이언트를 만들었다.
파싱이 실패하면 `ValidationError`가 날 거라 예상하고 그걸 잡는 코드를
써뒀는데, 실제로는 그 블록이 한 번도 실행되지 않았다. 대신 `response.parsed`가
아무 에러 없이 `None`으로만 남았다.

에러가 안 나니까 처음엔 정상 동작으로 보였다. 앞의 1번과 같은 종류의
착각이다.

### 원인

`google-genai` SDK 소스를 직접 열어봤다. 응답을 파싱하는 `_from_response`
안에서 `pydantic.ValidationError`와 `json.JSONDecodeError`를 자체적으로
`try/except: pass`로 삼키고 있었다. 파싱에 실패해도 예외가 밖으로 나오지 않고
`parsed`가 그냥 비는 구조였다.

이건 문서만 봐서는 알 수 없었고, 내가 쓴 `except` 블록이 죽은 코드라는 것도
실행해보기 전엔 몰랐다.

### 해결

예외를 기다리는 대신 `response.parsed is None`을 명시적으로 체크하도록
바꿨다. 그리고 `None`인 이유를 알아야 재시도할지 말지 정할 수 있으므로,
`candidates[0].finish_reason`을 직접 읽어서 판별하게 했다.

이때 차단 사유(SAFETY, PROHIBITED_CONTENT 등)를 나열해서 걸러내는 방식으로
먼저 짰다가 `PROHIBITED_CONTENT`를 빠뜨렸다. 그래서 반대로 뒤집었다. 정상
종료(STOP, LENGTH)일 때만 재시도 가능으로 보고 나머지는 전부 영구 실패로
처리한다. 차단 사유는 새로 추가될 수 있지만 정상 종료는 그렇지 않기 때문이다.

mock으로 정상 응답, 세이프티 차단, 파싱 실패, 토큰 초과, 응답 자체가 빈 경우
등 여러 시나리오를 만들어 각 분기를 실제로 타는지 확인했다.

### 느낀 점

1번은 내 코드가 예외를 숨긴 경우였고, 이번은 남이 만든 라이브러리가 숨긴
경우였다. 같은 함정이 층위만 다르게 반복된 셈이다.

"예외가 안 뜨면 정상"이라는 가정이 두 번이나 깨졌다. 이제는 라이브러리를 쓸 때
"실패하면 어떻게 알려주는가"를 먼저 확인하고, 애매하면 소스를 직접 열어보게
됐다.

## 3. 모델에게 시각 계산을 시켰더니 사고 과정이 출력 필드로 샌 사례

### 문제 상황

"내일 오전 10시에 알고리즘 복습"처럼 일정을 입력하면, 결과의 `title` 필드
안에 모델이 혼잣말하듯 계산하는 과정이 통째로 들어가 있었다. 한국어 사이에
영어 자기 교정 문장까지 섞여 있었고, 정작 필요한 `start_at`은 `None`이었다.

더 곤란한 건 재현이 일정하지 않다는 점이었다. 전날 같은 문장으로 돌렸을 땐
깨끗하게 나왔다. 될 때도 있고 안 될 때도 있으니 원인을 잡기가 더 어려웠다.

그리고 테스트는 계속 통과하고 있었다. 검증 코드가 `intent`가 맞는지만
확인하고 있었기 때문이다.

### 원인

처음엔 사고 예산을 최소로 설정한 게 원인인 줄 알았다. 하지만 의도별로 나눠서
보니 단서가 나왔다. `task`, `memo`, `research`는 멀쩡한데 `schedule`만
깨졌다. 그리고 시각 계산이 필요한 건 `schedule`뿐이었다.

당시 프롬프트는 모델에게 현재 UTC 시각을 주고 KST와의 9시간 차이를 직접
계산해서 넣으라고 시키고 있었다. 계산은 해야 하는데 그럴 공간이 없으니
추론이 출력 필드로 흘러나온 것으로 보였다. 사고 예산을 늘리면 확률은
줄겠지만, 산술 요구가 남아 있는 한 언제든 재발할 수 있는 구조였다.

### 해결

설정을 조정하는 대신 역할 분담 자체를 바꿨다.

1. 파이썬이 "오늘/내일/모레"가 며칠인지 미리 계산해서 프롬프트에 표로 넣어준다.
   모델은 날짜를 계산하지 않고 표에서 찾기만 하면 된다.
2. 모델은 시간대 변환 없이 로컬 시각만 출력하게 했다. 9시간 빼는 연산 자체가
   사라진다.
3. UTC 변환은 `ZoneInfo`를 붙여서 파이썬이 처리한다.
4. 프롬프트에 "각 필드에는 최종 값만 넣고 설명이나 계산 과정을 포함하지 마라",
   "title은 30자 이내" 규칙을 추가했다.

검증 코드도 고쳤다. `intent`만 보지 않고 `start_at`이 실제로 맞는 시각인지,
`title` 길이가 정상인지, 영어가 섞여 있지 않은지까지 확인하게 했다.

### 느낀 점

모델이 잘하는 일과 못 미더운 일이 다르다는 걸 실제로 봤다. 자연어에서 의미를
뽑아내는 건 잘하지만, 정확한 산술은 맡기면 안 된다. 결정론적으로 계산할 수
있는 건 코드가 하는 게 맞다.

검증 쪽 교훈이 더 컸다. 필드가 존재하는 것과 값이 올바른 것은 다른 문제인데,
`intent`만 확인하고 "통과"로 표시하고 있었다. 눈으로 결과를 직접 보지 않았으면
그대로 넘어갔을 것이다.

## 4. 프롬프트를 한 줄 고칠 때마다 다른 케이스가 망가진 사례 (3회 연쇄)

### 문제 상황

"오늘 자정에 마감"의 `start_at`이 오늘 00:00, 즉 이미 지나간 시각으로
계산되는 문제가 있었다. "오늘 자정"은 보통 오늘이 끝나는 시점(내일 00:00)을
뜻하는데 모델이 앵커 표의 날짜에 00:00을 문자 그대로 이어붙인 것이다.

이걸 고치는 것으로 시작해서, 결국 같은 유형의 회귀를 세 번 겪었다.

### 원인

**1차.** 자정 버그를 고치면서 규칙을 두 개 추가했다. 하나는 "자정은 내일
날짜의 00:00으로 계산하라"였고, 다른 하나는 안전장치로 넣은 "계산된 시각이
현재보다 과거면 안 된다"였다.

자정은 고쳐졌는데 "3시간 뒤에 전화하기"가 망가졌다. 원래는 모델이 현재
시각을 모르니 계산을 포기하고 `task` + `start_at=None`으로 안전하게 실패하던
케이스였다. 그런데 `schedule`로 잘못 분류하고 13시간 넘게 지난 엉뚱한 시각을
지어내기 시작했다. 현재 시각을 모르는 채로 "과거 금지"만 지키려다 그럴듯한
값을 만들어낸 것으로 보인다. 안전장치라고 넣은 규칙이 오히려 거짓말을 유도한
셈이다.

규칙을 제거하고 다시 확인해보니, 원래 고치려던 자정 문제는 첫 번째 규칙
하나만으로 이미 해결되어 있었다. 필요 없는 규칙을 안전해 보인다는 이유로
넣었던 것이다.

**2차.** 할 일에 마감 날짜를 추출하는 규칙("마감이 언급되면 `due_date`를
채워라")을 추가했다. 그러자 "오늘 자정에 프로젝트 마감이야"가 `task`로
분류되기 시작했다. 자정이라는 고정 시각이 있으니 `schedule`이어야 하는데,
"마감"이라는 단어에 끌려간 것이다. "마감과 함께 고정 시각이 언급되면
`schedule`"이라는 우선순위 규칙을 추가해 해결했다.

**3차.** 그런데 2차 수정에 넣은 예시 문구가 문제였다. 예시로 "3시"를 썼는데,
그것 때문에 "3시간 뒤에 전화하기"가 다시 `schedule`로 잘못 분류되고 과거
시각을 지어냈다. "3시"(오후 3시, 고정 시각)와 "3시간"(기간)이 문자열로 겹쳐서
표면적인 패턴 매칭을 유발한 것으로 보인다. 예시를 "오후 5시"로 바꾸고
"N시간·N분 뒤는 고정 시각이 아니다"를 명시해 해결했다.

### 해결

세 번 다 고친 뒤에는 반드시 스모크 세트 전체를 처음부터 다시 돌렸다.
2차와 3차는 그렇게 해서 발견한 것이고, 고친 케이스만 확인했다면 전부 놓쳤을
것이다.

### 느낀 점

프롬프트는 코드처럼 국소적으로 동작하지 않는다. 한 케이스를 고치려고 넣은
규칙이 전혀 다른 케이스의 동작을 바꿔버린다. 심지어 3차는 규칙이 아니라
**예시로 쓴 단어 하나**가 원인이었다. 무심코 고른 단어도 모델에게는 신호가
된다.

같은 실수를 세 번 반복하고 나서야 "프롬프트를 한 줄이라도 고치면 전체를
다시 돌린다"는 게 예외가 아니라 원칙이라는 걸 몸으로 익혔다. 이 프로젝트에서
가장 비싸게 배운 부분이다.

## 5. 폴백을 테스트할 방법을 고민하다 폴백 자체의 구멍을 발견한 사례

### 문제 상황

LLM 프로바이더가 실패하면 다음 프로바이더로 넘기는 폴백 체인을 만들어뒀다.
가짜 클라이언트로 시나리오를 만들어 검증은 마친 상태였는데, "실제 네트워크
장애를 어떻게 흉내 내서 진짜로 확인하지?"를 따져보다가 문제를 발견했다.

### 원인

`gemini.py`는 `except APIError`만 잡고 있었다. SDK 소스를 확인해보니
`google-genai`는 HTTP 에러 응답(401, 429, 500 등)만 `APIError`로 감싸고,
연결 자체가 안 되는 상황은 감싸지 않았다. `httpx.ConnectError`나
`httpx.TimeoutException`이 원본 그대로 새어나온다. 재현해서 확인했다.

이 예외는 내가 정의한 일시적 오류도 영구적 오류도 아니라서, 폴백 체인이
잡지 못하고 전체가 크래시된다. 설계 문서에는 "네트워크 장애는 폴백 대상"이라고
써놨는데, 정작 가장 흔한 네트워크 장애가 완전히 뚫려 있었던 것이다.

같은 코드를 옮겨 만든 다른 클라이언트는 이 문제가 없었다. `openai` SDK는
연결 장애를 자체적으로 감싸서 던지기 때문이다. SDK마다 예외를 어디까지
감싸는지가 달랐던 것이 원인이었다.

### 해결

연결 실패와 타임아웃을 일시적 오류로 분류하는 처리를 `APIError`보다 먼저
추가했다.

이때 `httpx.TransportError` 하나로 다 잡을 수도 있었지만 그러지 않았다.
거기에는 잘못된 URL 설정 같은 **내 실수로 생기는 예외**도 포함되어 있어서,
그것까지 일시적 오류로 분류하면 폴백이 순회하다 전부 실패하고 진짜 원인인
오타는 안 보이게 된다. 1번에서 겪은 것과 똑같은 함정이다. 그래서 타임아웃,
네트워크 오류, 프록시 오류만 골라서 잡았다.

**그리고 한 번 더 사고가 있었다.** 이 수정을 반영하고 확인까지 마쳤는데,
이후 다른 기능을 작업하면서 같은 파일을 다시 편집하는 과정에 이 블록이
통째로 빠진 채 "완성본"이 되어 있었다. 커밋 직전에 전체를 다시 실행해보고서야
발견했다.

### 느낀 점

테스트 방법을 고민하는 것만으로 설계 결함이 드러났다. "이걸 어떻게 검증하지?"
라는 질문에 답이 잘 안 나온다면, 그건 검증이 어려운 게 아니라 설계가 덜 된
것일 수 있다.

그리고 "예전에 확인했으니 됐다"가 안전하지 않다는 것도 배웠다. 같은 파일을
여러 번 오가며 편집하면 이미 고친 부분이 조용히 사라질 수 있다. 커밋 직전에
전체를 한 번 더 돌려보는 습관이 이번에 값어치를 했다.
