# Aiuto — 설계가 바뀐 과정

> 처음 설계에서 무엇을 왜 바꿨는지 기록한다.
> TROUBLESHOOTING이 무엇이 고장 났고 어떻게 고쳤는지를 다룬다면,
> 여기는 설계를 무엇에서 무엇으로 바꿨고 그 이유가 무엇이었는지를 다룬다.
>
> 항목 형식: [무엇이 바뀌었나] → [바꾼 이유] → [설계 이유] → [적용 결과]

---

## 1. v1 프로토타입에서 v2로 (2024.12 ~ 2026.07)

**[무엇이 바뀌었나]**
* v1: Django + Gemini 프로토타입. 입력한 일정·메모를 분류해 Notion에 정리하고, 일정별 준비 사항을 안내했다
* v2: FastAPI + Celery로 처음부터 다시 설계

**[바꾼 이유]**
* 직접 써 보니 매번 웹에 접속해 명령을 내리고, 결과는 Notion에서 따로 확인해야 하는 번거로움이 컸다

**[설계 이유]**
* LLM 호출은 응답까지 수 초가 걸려, 요청 접수와 처리를 나눴다(202 응답 + Celery 워커, README "요청 접수와 처리를 분리")

**[적용 결과]**
* 백엔드는 `/api/v1` JSON API와 OpenAPI 명세만 제공하고, 화면은 별도 레포에서 만든다(웹 → React → 앱, README "로드맵")

## 2. 저장소 · 식별자 · 세션 (2026.07)

**[무엇이 바뀌었나]**
* SQLite → PostgreSQL
* 정수 PK → UUID
* JWT `sub`: 이메일 → 사용자 UUID
* 동기 세션 → 비동기 세션(SQLAlchemy 2.0)
* 스키마 관리: Alembic 마이그레이션

**[바꾼 이유]**
* 여러 사용자가 동시에 쓰는 서버에서는 서버형 DB와 제약 조건 관리가 필요했다
* 순차 정수 PK는 식별자를 추측하기 쉬웠다
* 이메일은 바뀔 수 있는 개인정보라 토큰에 실을 이유가 없었다

**[설계 이유]**
* 다른 사용자의 레코드를 막는 것은 모든 조회에 거는 `user_id` 필터이고, UUID는 추측을 어렵게 하는 보조 수단이다
* 세션은 FastAPI의 비동기 처리에 맞춰 비동기로 바꿨다

**[적용 결과]**
* API는 `asyncpg`, 워커와 마이그레이션은 `psycopg` 동기 드라이버로 나눠 접속한다(README "API/워커 드라이버 이원화")

## 3. LLM 연결 방식 (2026.08)

**[무엇이 바뀌었나]**
* 로컬 모델(Ollama) 계획 → 외부 LLM API
* 외부 API는 `LLMClient` Protocol 뒤에 두어 구현체를 갈아 끼울 수 있게 했다

**[바꾼 이유]**
* 작은 서버에 실용적인 크기의 모델을 올릴 메모리가 없었다
* API 비용이 작아 로컬로 돌려 아낄 것이 없었다
* 작은 모델은 날짜 표현 해석 정확도가 떨어졌다

**[설계 이유]**
* 폴백 래퍼(`FallbackLLMClient`)도 같은 Protocol을 만족해, 호출부는 단일 클라이언트인지 체인인지 알 필요가 없다
* 상속이 아니라 조합으로 기능을 확장한다

**[적용 결과]**
* Gemini 구현체 하나로 운영한다
* 프로바이더 구성은 `LLM_CHAIN` 환경변수로 정한다(README "LLM 프로바이더 추상화")

---

## 4. 두 번째 프로바이더 (2026.08)

**[무엇이 바뀌었나]**
* NVIDIA NIM 폴백을 구현해 체인에 넣음 → 평가 후 체인에서 제외

**[바꾼 이유]**
* 대상 모델에서 구조화 출력 옵션이 실제로 출력 구조를 강제하지 못했다
* 한국어 출력이 손상됐다
* 스키마를 평탄화해도 같아서 모델 자체의 문제로 판단했다

**[설계 이유]**
* 구현체와 폴백 구조는 지우지 않고 `LLM_CHAIN`에서만 제외한다

**[적용 결과]**
* 조건을 만족하는 프로바이더가 생기면 환경변수만 바꾸면 된다(README "프로바이더 평가 결과")

## 5. 시각 계산을 맡는 쪽 (2026.08)

**[무엇이 바뀌었나]**
* 모델이 현재 시각을 받아 UTC로 변환 → 코드가 날짜를 미리 계산하고 UTC로 변환

**[바꾼 이유]**
* 모델의 계산 과정이 출력 필드에 섞여 나왔다
* 재현도 일정하지 않았다(TROUBLESHOOTING 3·4)

**[설계 이유]**
* 결정할 수 있는 계산은 LLM이 아니라 코드가 한다
* 파이썬이 오늘·내일·모레 날짜를 계산해 프롬프트에 표로 넣고, 모델은 표에서 찾아 로컬 시각만 출력한다

**[적용 결과]**
* UTC 변환은 `ZoneInfo`로 코드가 한다(README "시각 처리")
* "결정할 수 있는 계산은 코드가 한다"를 프로젝트 규칙으로 두었다

---

## 6. 할 일의 마감 (2026.08)

**[무엇이 바뀌었나]**
* 할 일 마감(`due_date`): 시각이 있는 타입 → 날짜(`DATE`) 타입

**[바꾼 이유]**
* "금요일까지"에 시각을 붙이려면 모델이 몇 시인지 지어내야 했다
* "자정까지" 같은 표현은 어느 날짜에 속하는지 모호했다

**[설계 이유]**
* 시각이 분명한 입력은 처음부터 일정(`schedule`)으로 분류하는 것이 도메인 정의에 맞다

**[적용 결과]**
* 시각이 분명한 마감 입력은 일정으로 분류된다(README "시각 처리")

---

## 7. UTC 변환 책임 (2026.09)

**[무엇이 바뀌었나]**
* LLM 클라이언트와 워커가 각각 변환 → LLM 클라이언트만 변환

**[바꾼 이유]**
* 두 계층이 모두 변환해 시각이 9시간 어긋났다
* 변환이 틀린 게 아니라 누가 변환하는지 정하지 않은 것이 원인이었다(TROUBLESHOOTING 7)

**[설계 이유]**
* 변환 책임을 한 계층에만 둔다

**[적용 결과]**
* "LLM 클라이언트는 항상 UTC로 변환한 시각을 반환하고, 워커는 시간대 변환을 하지 않는다"를 계층 간 규칙으로 두었다

## 8. 개발 순서 (2026.10)

**[무엇이 바뀌었나]**
* 다음 기능(조회·수정·삭제)부터 → 자동 테스트 → CI → Linux 서버 배포를 먼저

**[바꾼 이유]**
* 그때까지 만든 부분이 맞게 동작한다는 근거가 수동 확인과 재현 스크립트뿐이었다
* 기능을 더 얹으면 확인할 범위만 커진다
* 비서를 실제로 쓰려면 내 PC가 꺼져 있어도 돌아가는 서버가 있어야 했다

**[설계 이유]**
* 이후 모든 기능은 테스트와 CI를 통과한 뒤에만 합친다

**[적용 결과]**
* 첫 자동 테스트는 TROUBLESHOOTING 8번의 중복 처리 재현 시나리오를 옮기는 것이다(README "로드맵")
